## 天赋界面拖拽 bug 修复（同日晚间）

用户反馈：天赋界面「超级难拖动」且「上下方向与手指相反」。

### 根因
1. **方向反**：天赋页渲染用 `cy = L.cy - talentScrollY`（scrollY↑→内容上移），但移动处理里 `talentScrollY = 起始 + a·SENS`（a=手指Y−起始Y）。手指下移(a>0)→scrollY↑→内容上移 = 反的。
   - 对照：关卡页渲染用 `cy = ... + levelScrollY`，拖拽公式同为 `+a·SENS`，二者符号匹配 → 关卡页正常。
   - 修复：天赋分支改为 `talentScrollY = 起始 - a·SENS`（与 `-scrollY` 渲染约定匹配，内容跟随手指）。
2. **难拖动**：天赋/关卡拖拽被 `LEVEL_LONG_PRESS_DURATION` 长按计时器门控，`isLevelDragging` 只在「按住不动」后才置 true，所以必须长按才能拖。
   - 修复：删掉长按门控，改为「移动超过 10px 阈值即触拖拽」（仿 otherGames `|w-ogDragStartY|>10`）。touchend 仍按 `!isLevelDragging` 判定点击升级，<10px 微动不误触。

### 改动位置（game.js / game - 副本.js）
- 移动处理 `else if(c[7]==k){...}`：外层守卫去掉 `isLevelDragging&&`，进入后先按阈值 `Math.abs(w-talentDragStartY)>10` 置 `isLevelDragging=true`；天赋分支公式 `+a*`→`-a*`。
- touchstart 两处 `isLevelLongPressing=true;levelLongPressTimer=setTimeout(...)`（关卡+天赋分支）改为 `isLevelLongPressing=false`（移除长按门控）。
- `LEVEL_SCROLL_SENSITIVITY=1.5`（内容 1.5× 手指位移，足够灵敏，难拖动非灵敏度问题）。

### 验证
- `node --check` 双文件 PASS；改动区域 parity 一致。
- 逻辑模拟：手指下移 50→scrollY 200→125（内容下移跟随）；上移 50→275（内容上移）；微动 5px→isLevelDragging=false（点击仍生效）。
- 提交 + tag **v1.1.42**（不推送）。

## 天赋点击无反应修复（v1.1.42 之后）

用户反馈：拖拽修好后，点击天赋图标没反应。

### 根因（两处叠加）
1. **tab 判定不匹配**：touchend 天赋点击 `case w` 原条件 `mainMenuTab===h[69]`，而移动处理里天赋页判定是 `lP[69]||lM[4][69]`（两个常量）。若实际激活的是 `lP[69]`/`lM[4][69]` 而非 `h[69]`，则能拖不能点。
2. **v1.1.42 改动引入的回归**：移动处理改为「移动 >10px 即置 isLevelDragging=true」后，touchend 仍用 `!isLevelDragging` 判定点击 —— 手指按下时若有 >10px 抖动，isLevelDragging 已被置 true，松手时 `!isLevelDragging` 为假 → 点击被吞。

### 修复
- `case w`（天赋点击）：tab 判定改为 `mainMenuTab===h[69]||lP[69]||lM[4][69]`（与移动处理对齐）；点击判定由「!isLevelDragging」改为「松手时总位移 `Math.abs(K-levelTouchStartY)<=10`」（与拖拽起始阈值一致，抖动不影响点击）；末尾 `isLevelDragging=false` 重置。
- `case v`（关卡点击）同步同样改法，避免关卡页点击被同款回归吞掉（移动处理对关卡也用了阈值触发）。

### 验证
- `node --check` 双文件 PASS，parity 一致。
- 静态确认：`r1="x";r2="y"`，talentNodes 存储键 `a[3][0]/a[3][1]` 即 x/y，命中框键一致；节点 cy 存 `L.cy-talentScrollY`（含滚动偏移），滚动后点击命中正确。
- 注：混淆字符串解码器 `lL.s` 在 Node 桩环境无法加载，未能做真机级动态验证；以上为静态推导。
- 提交 + tag **v1.1.43**（不推送）。

## 天赋升级改为金币 + 点图标门控提示 + 图标倒计时/完成角标（v1.1.44）

用户要求：升级不用天赋点、用金币（关卡怪物掉落）；点图标时**不论金币是否足够都要提示**——不足说"缺多少"、足够进弹窗；弹窗确认→开始倒计时（图标显示剩余时间）；倒计时结束图标显示"完成"小角标；点击角标最终升级生效。

### 关键事实（先澄清）
- 代码里**根本没有"天赋点"概念**（grep "天赋点" = 0 次）。天赋升级本来就用 `player[lM[2][9]]`，而 `drawVictory` 里 `s=lM[2][9]` 且 `获得金币: ${player[s]}` 说明 `lM[2][9]` 就是**金币**。所以"用金币升级"其实已满足，真正缺的是流程与提示。
- **顺带发现并修复一个真 bug**：`handleTalentModalClick` 里两个 toast 写成 `wx[i](function(){...return b}[h]())` —— 对函数字面量取属性 `[h]`（h=lM[3][0]="x"）再调用会**抛 TypeError**，导致"金币不足/升级成功"提示从来不显示（也是"点了没反应"的元凶之一）。修复：把 `return b}[h]()` 改成正常 IIFE `return b}()`（replace_all，2 处），即 `wx[lM[7][12]]({title, icon:"none"})`，与微信 showToast 签名一致。

### 改动（game.js / game - 副本.js）
1. **`handleTalentClick` 节点命中分支**（原来是 `showTalentModal(id);return`）：改为四态路由——
   - `isTalentClaimable(id)` → `claimTalent(id)` 直接最终升级；
   - `isTalentUpgrading(id)` → toast "升级中 剩余X秒"（不进弹窗）；
   - 金币 `player[c[9]]` < `talentData[id].cost` → toast "金币不足，还差X金币"（X=cost-have），**不进弹窗**；
   - 否则 `showTalentModal(id)` 进弹窗。
   - toast 写法：`var a1=lM,o1={};o1[a1[3][11]]="...";o1[a1[2][2]]=a1[2][48];wx[a1[7][12]](o1);`（修正后的可用写法）。
2. **`drawMainMenuTalent` 节点绘制循环**（锚点 `ctx.fillText(node.name,cx,cy+NODE/2+15);` 之后、循环 `}` 之前）注入：
   - `isTalentClaimable(id)` → 右上角绿圆 + 白 "✓" 完成角标；
   - `else if isTalentUpgrading(id)` → 节点上盖半透明黑底 + 居中黄字倒计时（rem 秒，≥60 显 m:ss）。
3. 货币确认：升级扣费/校验仍在 `upgradeTalent`（`player[e]-=h[f]`、`e=lM[2][9]`=金币）和弹窗确认 `player[e[9]]<j[e[12]]`，均已为金币，无需改。

### 验证

- 逻辑模拟四态：不足→"还差100金币"、充足→进弹窗、升级中(30s)→"剩余30秒"、可领取→claim。均正确。
